# 文档工作台 UI —— 空状态与边界情况

`docs/ui-document-workspace.md` 的补充。主文档写的是正常路径，这份写不正常的路径。
每条都给了建议处理方式，不是只列问题。

---

## 1. 空状态

| 场景 | 建议 |
|---|---|
| 文档一条批注都没有 | 批注 tab 显示引导：如何选中文字创建批注。**同时给一个「让 AI 通读一遍」的入口** —— 这是冷启动最自然的方式：AI 读完直接产出一批批注 |
| 有批注，一个话题都没有 | 话题 tab 引导：去批注 tab 选几条开个话题。不要只显示"暂无数据" |
| 话题刚建好，还没发消息 | 引用卡片已预填，对话区显示这个话题涉及哪几条批注的摘要，提示可以直接问。**别显示空白** |
| 所有批注都已解决 | 文档上无标记，批注 tab 显示"全部处理完毕"+ 一个「查看已解决(N)」的入口。已解决的批注**不能彻底消失**，用户要能回溯 |
| 冷话题历史为空 | 不应存在。若出现（建了话题没发消息就关了），当作空话题处理，并允许直接删除 |

**通用原则**：这个系统的空状态往往是"还没开始协作"，而不是"没有数据"。
引导语应该指向下一个动作，而不是描述当前的空。

## 2. 数量与密度

### 2.1 锚点密集

**同一个 block 上有多条批注** —— 很常见。不要让标记重叠。

建议：同 block 的标记聚合成一个，显示最高优先级的图标 + 总数（例如 `★3`），
点击展开列出这几条。优先级顺序按主文档 §9。

**长文档 + 几十条批注** —— 页边一整列标记。可接受，因为它们锚定在真实位置上，
用户滚动时是渐次出现的，不会同时挤在一屏里。

建议加一个**文档滚动条上的位置指示**（minimap 式的小刻度），让用户不滚动也知道
"下面还有 3 个 ★"。这是唯一值得增加的密度辅助。

### 2.2 popover 列表过长

一条批注被 5 个以上话题讨论过时，点击标记弹出的话题列表会很长。

建议：只列**活跃**话题（有在跑/等你/有未读的），冷话题折叠到"还有 N 个历史话题"。
因为用户点这个标记是想"去处理它"，不是想考古。

### 2.3 引用卡片区爆炸

一个话题聊到后面可能积累了几十条引用。

建议：引用卡片区**默认折叠**，只显示 `引用 5 项 ▾`。展开后按类型分组。
不要让它把对话区挤到屏幕外。

### 2.4 超长对话

一个话题聊几百轮是可能的（AI 一轮回复本身就很长）。

建议：虚拟滚动 + "跳到最新"浮标。历史消息可折叠。
**默认滚动位置**：有未读时定位到第一条未读，无未读时定位到底部。

### 2.5 引用内容被后端截断

引用一篇很长的文档时，后端会截断内容再发给 AI，并标记 `truncated`。

建议：引用卡片上显示"已截断"的标记，hover 说明"文档过长，AI 只看到了前 N 个段落"。
**这个必须显式告知** —— 否则用户会以为 AI 看了全文，然后困惑于它为什么漏掉了后半部分。

## 3. 锚点失效（重要）

批注挂在**文档**上而不是某个 revision 上 —— 这是刻意的设计，好处是文档改了批注不丢。
代价是：**批注锚定的那个 block，可能在后续修改中被改掉或删掉了。**

批注保存了三个可选的快照字段：block_id、block 原文快照、选中文本快照。

| 情况 | 建议 |
|---|---|
| block 还在，内容没变 | 正常锚定 |
| block 还在，**内容已改** | 正常锚定，但标出"原文已变更"，可展开看当初的快照 |
| block **已删除** | 批注**不能消失**。移到批注列表顶部的「已失去锚点 (N)」分组，展示原文快照，让用户判断是否已经被解决了 |
| 批注本来就没有 block_id（整篇文档级的意见） | 正常情况，不是错误。批注列表里单独一组"文档级批注"，文档正文上不显示标记 |

失去锚点的批注**在文档正文上无处可标**，所以它只能活在右栏列表里。
这是"没有位置的东西不上文档"这条原则的又一个应用。

---

## 4. 引用失效

主文档 §8 提过：引用的东西被删了，消息会被**整条拒绝**发送，而不是丢掉那条引用照发。

UI 需要：

1. 发送失败时，消息**留在输入框**，不要丢失用户输入
2. 明确指出是**哪一条**引用失效了（后端会返回类型和 id）
3. 提供「移除这条引用并重发」的一键操作
4. 引用卡片上把失效项标成红色/划掉

```
┌────────────────────────────────┐
│ ⚠ 发送失败：引用的批注已被删除    │
│   📌 批注 3（已失效）  [移除]     │
│                    [移除并重发]  │
└────────────────────────────────┘
```

**不要**静默丢弃失效引用后照常发送。半个问题比没问题更糟 ——
AI 会对着它根本没看到的内容自信作答，而用户不知道。

## 5. 会话异常

| 场景 | 建议 |
|---|---|
| AI 回到一半，后台进程退出 | 话题转 ◌ 冷态，**已收到的部分内容保留并标记"回复未完成"**，提供「重试」。不要把半截回复删掉 |
| 冷话题恢复失败 | 明确报错，历史消息仍可读（它们是存好的），只是不能继续对话。提供重试 |
| 网络断开 | 话题状态显示"连接中断"，重连后**主动拉取一次状态**。断线期间 AI 仍在后台跑，重连后可能已经跑完了 |
| 用户关掉标签页再回来 | 状态应完整恢复，包括"有一个提问在等你"。**这是常态不是异常** |
| 同一话题在两个标签页打开 | 两边都能收到同样的推送。回答提问时先到先得，另一边应看到"已被回答" |
| 提问已被回答，但界面还显示着提问 | 收到"该提问已解决"的推送后，把控件替换成只读的已选结果 |

**关于"AI 还在跑"**：整个系统的前提是任务长时、用户会离开。
任何"离开就中断"或"刷新就丢失"的行为都是 bug，不是简化。

## 6. 多人协作冲突

| 场景 | 建议 |
|---|---|
| 别人新建了批注 | 实时插入列表和文档标记。**不要打断用户当前操作**，不要自动滚动 |
| 别人解决了你正在讨论的批注 | 该批注锚点标记消失，但**话题里的引用卡片保留**并标注"已解决"。话题不受影响，聊天可以继续 |
| 别人删了你正在讨论的批注 | 引用卡片标为失效（同 §4）。已发出的历史消息不变 —— 它们记录的是当时的事实 |
| 同一条批注同时被两个人追评 | 追加即可，按顺序排列。无需冲突处理 |
| 两个话题同时讨论同一条批注 | **正常情况，不是冲突**。锚点标记显示数字 2 |
| 两个人同时改同一篇文档 | 超出本规格范围，由文档编辑器自身处理 |

注意：本系统的参与者模型**不含权限概念** —— 不要设计"只有创建者能解决批注"
之类的规则，也不要显示锁定/占用状态。

## 7. 时间与陈旧

| 场景 | 建议 |
|---|---|
| 一个提问已经等了三天 | ❓ 状态不随时间衰减，但显示"已等待 3 天"。**等得越久越该处理，不是越该忽略** |
| 话题很久没动 | 显示相对时间。超过一定时长自动转冷是后端行为，UI 只需正确反映 |
| 批注 ○ 了很久 | 不做特殊处理。堆积是事实，不是问题（主文档 §4.3） |
| 时间显示 | 一小时内相对（"5 分钟前"），当天显示时刻，更早显示日期。hover 出完整时间 |

## 8. 窄屏 / 移动端

两栏布局在窄屏下站不住。建议**降级为单栏 + 底部切换**：

```
┌──────────────────┐
│                  │
│   文档 / 批注 /   │
│   话题（三选一）   │
│                  │
├──────────────────┤
│ [文档] [批注3] [话题1] │
└──────────────────┘
```

关键：**❓ 和 ★ 的角标必须在底部切换栏上始终可见**。窄屏下用户看不到全貌，
"哪里需要我"这个信息比宽屏更重要，不是更不重要。

打开话题详情时，左侧文档高亮那条规则在窄屏下失效（看不到文档）——
用补偿：话题详情顶部的引用卡片改为默认展开，让用户至少知道在聊哪几条。

## 9. 首次使用

不建议做分步引导浮层。建议用空状态本身承担引导（§1），加一条：

**首次打开一篇有内容但无批注的文档时**，把「让 AI 通读一遍」做成主按钮。
这是整个产品最短的价值路径：一次点击 → 一批批注 → 用户有东西可以聊了。

## 10. 提案、争用与提交

| 场景 | 建议 |
|---|---|
| **提交时文档已被别人改过** | 提交失败。这是真实冲突，必须让人看见：提示"文档已更新到新版本"，提供重新审阅入口。**不要静默重试或强行覆盖** |
| 你正在裁决，第三个话题又提了一版 | 界面提示"出现了新版本"，让人主动刷新。不要在人正在读的时候悄悄插入一列 |
| 某段落有 3 个以上提案 | 横向滚动或改纵向列表，出口不变（选一个 / 开话题决定） |
| 提案所属的话题已转冷 | **提案照常有效，可正常裁决。** 提案的存活不依赖话题是否还在跑 |
| 提案所属的话题被归档 | 同上。提案上仍显示来源话题名，可点进去看（只读） |
| 落选话题后续又提了一版 | 允许。这是一条新的活跃提案，该段落重新进入争用状态 |
| 提交后，话题里还引用着那条提案 | 引用卡片标为"已采纳并提交"，可点击跳到对应文档版本。**不是失效引用** |
| 落选提案在话题里被引用 | 标为"未采纳"，内容仍可查看。**不要因为落选就让它变成失效引用** |
| 一次提交涉及很多段落 | 提交界面按文档分组后仍可能很长。支持按文档折叠，并显示每篇的改动计数 |
| 提交界面里全是争用 | 「提交」按钮禁用并说明原因，而不是提交一个空的版本 |

**贯穿原则**：提案是独立持久化的资源，它的生命周期**不跟随**创建它的话题。
话题冷了、归档了、甚至提案落选了，提案本身都还在，只是状态不同。
任何"话题没了提案就失效"的设计都是错的。

## 11. 需要产品确认的开放问题

这几条我没定，设计时先按建议做，但值得回头确认：

1. **话题能不能删？** 建议不能硬删，只能归档 —— 它是"为什么这样改"的唯一记录。
   但用户误建的空话题应该能删。
2. **批注能不能重新打开？** 已解决的批注若发现改错了，建议允许回到未决状态，
   并在追评里留下痕迹。
3. **AI 主动发起话题吗？** 目前设计里话题都由人建。如果允许 AI 主动开话题，
   话题列表需要一个"AI 发起"的标识，且不应默认占用角标。
4. **跨文档话题怎么进入？** 话题本身不属于任何文档，可以引用多篇。
   当前设计里话题列表挂在文档工作台下，跨文档话题需要一个全局入口 —— 建议二期再做。
