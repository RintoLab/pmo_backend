# 文档工作台 UI 规格

给页面设计用的交接文档。读者不需要了解后端实现，但需要严格遵守这里的状态定义和「明确不要」——
它们不是审美偏好，每一条背后都有具体的失效场景，文中都写了原因。

---

## 1. 这是什么

一个 **AI 协同审阅文档** 的工作台。人和 AI 一起读同一篇文档、就具体段落交换意见、讨论，
最终由人决定是否修改文档。

三个核心概念，必须分清：

| 概念 | 是什么 | 类比 |
|---|---|---|
| **文档 (document)** | 被审阅的对象，由若干 block（≈段落）组成 | 一篇 Google Doc |
| **批注 (annotation)** | 锚定在文档某处的**一条意见**，可有多条追评 | Google Doc 的评论串 |
| **话题 (conversation)** | 一次**多轮对话**，可同时讨论多条批注 | 一个聊天会话 |
| **提案 (proposal)** | 某个话题对某个段落提出的**一版改写**，未生效 | 尚未合并的改动 |
| **提交 (commit)** | 人选定若干提案，固化成文档的新版本 | 保存一个版本 |

**贯穿全系统的不变量：人不直接写文档，人只做决定。**
AI 写，人审、人选、人提交。界面上任何地方都不应出现"让人手动编辑一段正文"的入口 ——
想要一个不同的版本，正确路径是回到话题里说，由 AI 写出来。

提案的关键规则：**一个话题在一个段落上只有一条提案**（反复修改是就地更新）。
所以同一段落上出现 2 条以上提案，必然来自**不同话题** —— 这就是"争用"，需要人裁决。

关键关系：

- 批注**有位置**（锚定在某个 block 或某段选中文本上）
- 话题**没有位置**。一个话题可以同时讨论分布在文档三处的批注，甚至跨多篇文档
- 批注 ↔ 话题是**多对多**：一个话题聊 N 条批注，一条批注也可能出现在多个话题里
- 对话是**过程**，批注是**结论**。AI 在话题里聊完，会把结论写回成某条批注的一条追评

参与者（actor）有人和 AI 两种，**在批注和对话里是对等的** —— AI 可以主动提批注、发追评，
人也可以。UI 上需要区分头像/标识，但不要把 AI 的发言做成"系统消息"那种次等样式。

## 2. 现状与目标

**现在有的**：两栏，左侧文档，右侧批注列表。

**要加的**：多个可并发的话题。用户可以同时开好几个话题（比如一个聊命名一致性、
一个聊术语表对齐），发完消息就切走干别的，AI 在后台跑，跑完或需要提问时通知用户。

**核心难点**：并发之后，用户随时可能有 2-3 个话题在不同状态，屏幕不能被状态提示淹没，
但又不能让"需要用户处理"的事被埋掉。整份规格基本都在解决这个平衡。

## 3. 布局

### 3.1 总体：两栏，右栏是两个可切换视图

```
┌────────────────────────────────┬──────────────────────┐
│                                │  [ 批注 3 ] [ 话题 1 ]│  ← 视图切换 + 角标
│  文档正文                       ├──────────────────────┤
│                                │                      │
│  ▍段落一…              ○       │  当前视图内容          │
│                                │                      │
│  ▍段落二…              ★       │                      │
│                                │                      │
│  ▍段落三…                      │                      │
│                                │                      │
└────────────────────────────────┴──────────────────────┘
     主体，宽度优先                    固定宽度侧栏
```

**不要开第三栏放对话。** 三栏会把文档挤扁，而讨论文档时最需要看的恰恰是文档。
批注列表和对话窗几乎不需要同时全神贯注 —— 话题一旦建好，它涉及的批注内容已经作为
引用卡片显示在对话顶部了，列表的使命就完成了。

**不要用弹窗（modal / dialog）承载对话。** 它直接遮住文档，是比第三栏更糟的方案。

### 3.2 右栏视图 A：批注列表（默认）

就是现有的批注列表，每行需要能表达该批注的状态（见 §5.1）。
支持**多选**，因为「选中若干条批注 → 开一个话题聊它们」是建话题的主要入口。

```
┌──────────────────────┐
│ [ 批注 3 ] [ 话题 1 ] │
├──────────────────────┤
│ ☑ 批注 1        ○    │
│   "这里的命名和…"      │
│                      │
│ ☐ 批注 2        ★    │
│   "术语表里是…"        │
│                      │
│ ☑ 批注 3        ◐    │
│   "这段的结论…"        │
├──────────────────────┤
│ 已选 2 条            │
│ [ 开个话题聊这些 ]     │  ← 有选中时才出现
└──────────────────────┘
```

### 3.3 右栏视图 B：话题列表

```
┌──────────────────────┐
│ [ 批注 3 ] [ 话题 1 ] │
├──────────────────────┤
│ ❓ 命名一致性          │  ← 等你回答，排最前
│    3 条批注 · 2 分钟前 │
│                      │
│ ⏳ 术语表对齐          │
│    2 条批注 · 进行中   │
│                      │
│ ○ 结构调整            │
│    1 条批注 · 昨天     │
│                      │
│ ◌ 早期讨论            │  ← 冷话题，灰
│    5 条批注 · 上周     │
├──────────────────────┤
│ [ + 新话题 ]          │
└──────────────────────┘
```

排序：**按需要用户处理的紧迫度**，不按时间。❓ > ● > ⏳ > ○ > ◌，同档内按最近活动倒序。

### 3.4 右栏视图 B':话题详情（从话题列表下钻）

**这是下钻，不是新面板** —— 替换掉话题列表的内容，左上角有返回。

```
┌──────────────────────┐
│ ← 命名一致性      ⋯   │
├──────────────────────┤
│ ┌──────────────────┐ │
│ │引用              │ │  ← 引用卡片区，可折叠
│ │ 📌批注1 📌批注3   │ │
│ │ 📄需求文档        │ │
│ │ [+ 添加引用]      │ │
│ └──────────────────┘ │
│                      │
│  你：这两条说的是…     │
│                      │
│  AI：我看了一下…       │
│      （流式输出中）    │
│                      │
├──────────────────────┤
│ [输入框         ] [↑]│
└──────────────────────┘
```

打开话题详情时，**左侧文档要高亮这个话题引用的所有批注锚点**。
右栏虽然被对话占满了，用户在文档上依然看得见"我们正在聊哪几处"。
这是不开第三栏还能保持上下文的关键，不能省。

## 4. 文档区的标记

文档正文上有**两套独立的标记**：批注锚点（§4.1–4.3）和段落改动（§4.4）。
它们锚定的对象不同，可能同时出现在同一行，必须视觉可区分。

### 4.1 批注锚点：四档

| 样式 | 条件 | 含义 |
|---|---|---|
| ○ 空心 | 未解决，当前没有话题在讨论它 | 待办，但不急 |
| ◐ 实心/脉冲 | 有话题正在讨论它 | AI 正在弄，你可以不管 |
| ★ 高亮（最扎眼） | **有结论待你处理** | **该你了** |
| 无标记 | 已解决 / 已驳回 | 完成 |

★ 是整个界面里视觉权重最高的元素，它标记的是 AI 把活儿交回给人的那一刻。

### 4.2 多对多怎么标

标记的语义是「**这条批注的状态**」，它**不试图指向某一个话题**。所以一条批注被 2 个话题
同时讨论完全不冲突 —— 标记旁边显示数字 `2` 即可。

点击标记 → popover 列出涉及它的话题：

```
   ◐2  ──→  ┌─────────────────────┐
             │ 讨论这条批注的话题：   │
             │  · 命名一致性  ⏳     │
             │  · 术语表对齐  ❓     │
             └─────────────────────┘
```

选一个 → 右栏切到该话题详情。

反向导航：话题详情顶部的引用卡片，点任一条批注 → 文档滚动到该处并高亮。
两个方向都能走通，**全程不需要任何悬浮元素**。

### 4.3 标记何时消失（最容易做错的一条）

**只有当批注被标记为「已解决」或「已驳回」时才消失** —— 也就是人真的做了决定。

**不要按"用户看过了"来清除。** 那会导致：AI 讨论完写回结论 → 用户瞄了一眼 →
标记消失 —— 可这条批注根本没解决，文档也没改，它就这么从视野里没了。
而这恰恰是最需要用户处理的时刻。

○ 会随时间堆积，这是可以接受的：那不是噪音，是"你确实有 20 条没处理"这个事实。
真正需要避免的是**讨论痕迹**的堆积 —— 那个已经解决了，话题跑完后标记会从 ★/◐ 退回 ○。

### 4.4 段落上的改动标记（与批注标记并列，不是同一套）

批注标记锚在**批注**上；改动标记锚在**段落**上。两者可能出现在同一行，需要视觉上可区分
（建议：批注标记在页边，改动标记贴着段落本身，如左侧竖条）。

| 样式 | 条件 | 含义 |
|---|---|---|
| 无 | 该段落没有任何提案 | 未被改动 |
| ▍蓝色竖条 | 恰好 1 条提案 | 有改动，无争议，提交时默认采纳 |
| ▍**红色竖条 + 数字** | **≥ 2 条提案** | **争用，等你裁决** |

争用标记的视觉权重与 ★（批注有结论待处理）同级 —— 都是"该你了"。

点击标记：
- 1 条提案 → 就地展开对比：原文 / 新版，标注来自哪个话题
- ≥ 2 条 → 进入争用裁决界面（§7.7）

注意：改动标记**不会随时间自动消失**，它一直存在到该段落被提交或提案被裁决掉。
这跟批注标记是同一个原则（§4.3）：由决定清除，不由"看过了"清除。

## 5. 状态系统

### 5.1 批注状态（用于文档锚点 + 批注列表）

| 图标 | 状态 | 判据 |
|---|---|---|
| ○ | 未决 | `status = open`，无关联的活跃话题 |
| ◐ | 讨论中 | 有话题正在讨论它 |
| ★ | 有结论待处理 | 有来自话题的新结论，且 `status` 仍为 `open` |
| — | 已完成 | `status = resolved` 或 `dismissed` |

### 5.2 话题状态（用于话题列表）

| 图标 | 状态 | 判据 | 需要人吗 |
|---|---|---|---|
| ❓ | **等你回答** | AI 停下来问了个问题，在等 | **是，最高优先级** |
| ● | 有新消息未读 | 上一轮跑完了，有你没看过的内容 | 是 |
| ⏳ | 进行中 | 消息已发出，AI 还在回 | 否 |
| ○ | 闲置 | 没在跑，也没有未读 | 否 |
| ◌ | 冷 | 后台资源已回收，点开会自动恢复 | 否 |

⚠️ ❓（话题等你回答）和 ★（批注有结论待处理）是**两件不同的事**，
视觉上必须明显可区分，不要用同一个符号或同一个颜色。

### 5.3 角标：每个 tab 只报自己的事

- **批注 tab 角标** = ★ 的数量（有结论待你处理的批注数）
- **话题 tab 角标** = ❓ 的数量（等你回答的话题数）

**角标只统计"需要你行动"的，不统计总数。** 正在跑的话题不该占用户的注意力预算 ——
它跑完了自然会变成 ● 或 ★。

### 5.4 「等你回答」不能省

后端的提问是**永不超时**的：AI 停下来问一个问题，如果没人回答，它会一直等下去，
同时占着后台资源。所以 ❓ 状态必须在折叠态（没打开话题详情时）可见。

**这是整个并发设计里唯一不能省略的 UI 元素。** 如果用户看不到"哪个话题在等我"，
话题就会静默地永久卡死。

## 6. 屏幕上只有四处状态

清点一遍，全局只有这四个地方显示状态：

1. **tab 角标** —— 需要你行动的数量（§5.3）
2. **文档上的标记** —— 批注锚点（§4.1）+ 段落改动（§4.4）
3. **话题列表每行的状态图标** —— 展开话题 tab 后才可见（§5.2）
4. **文档顶部的改动条** —— 见下

### 6.1 文档顶部的改动条

文档正文上方常驻一条，它是提交流程的唯一入口：

```
┌────────────────────────────────────────────────┐
│  8 处改动待提交    ⚠ 2 处争用      [ 审阅并提交 ]│
└────────────────────────────────────────────────┘
```

- 无任何提案时整条隐藏
- 有争用时，争用数标红；**「审阅并提交」仍可点**（进去后争用项被拦住，其余仍可提交）
- 这条也解决了"改动散落在长文档各处、滚动才看得见"的问题：
  数字告诉你有多少，点击可跳转到第一处

滚动条上建议加位置刻度（同 `edge-cases.md` §2.1），把 ★、争用、改动的位置标出来。

### 明确不要做

| 不要 | 原因 |
|---|---|
| 最小化的聊天气泡 | **话题没有位置。** 一个话题引用了分布在文档三处的批注，它的锚点是哪个？没有答案。任何悬浮物都得在这件事上撒谎，而多对多一来这个谎就穿帮了 |
| 屏幕角落的悬浮卡片列 | 同上。有位置的（批注）才上文档，没位置的（话题）只待在右栏列表里 |
| toast / 消息弹出提示 | 话题是长时任务，用户会主动切走。toast 转瞬即逝，正好错过 |
| 第三栏 | 挤扁文档（§3.1） |
| 弹窗承载对话 | 遮住文档（§3.1） |
| 未读消息数徽章（按条数） | AI 一轮回复可能几十条流式片段，条数没有意义。用"有/无未读"即可 |

## 7. 关键流程

### 7.1 建话题

1. 批注列表里勾选若干条（也允许 0 条，直接开空白话题）
2. 点「开个话题聊这些」
3. 右栏切到话题详情，引用卡片区已预填这几条批注
4. 光标落在输入框
5. 发出第一条消息

也可以从话题列表的 `[+ 新话题]` 开始，再手动添加引用。

### 7.2 引用不止批注

引用可以是四种类型，输入框需要一个 mention 选择器（如 `@`）来添加：

| 类型 | 说明 |
|---|---|
| 批注 | 一条批注及其全部追评 |
| 文档 | 整篇文档的当前内容 |
| 项目 | 项目信息 + 其下文档的索引 |
| 附件 | 图片，会作为图片发给 AI |

引用是**逐条消息**携带的，不是话题级的 —— 用户可以在聊到一半时再拉进来一条批注。
引用卡片区展示的是"这个话题到目前为止涉及过的所有引用"的并集。

### 7.3 发完就走

这是并发的核心体感，必须顺畅：

1. 发出消息，话题变 ⏳
2. 用户直接点返回 / 切到批注 tab / 开另一个话题
3. **后台继续跑，不受影响**
4. 跑完 → 话题变 ●，话题 tab 角标不变（● 不进角标）
5. 若中途 AI 提问 → 变 ❓，话题 tab 角标 +1

用户不应该觉得"我得守着它"。

### 7.4 回答 AI 的提问

AI 有四种提问形式，需要四种控件，都渲染在对话流里（不要用弹窗）：

| 形式 | 控件 | 返回 |
|---|---|---|
| 单选 | 选项列表 | 选中项 |
| 确认 | 是 / 否 | 布尔 |
| 输入 | 单行输入框 | 文本 |
| 长文本编辑 | 多行编辑区 | 文本 |

四种都必须提供**「取消 / 跳过」**，AI 会把取消当作"用户拒绝回答"并继续往下走。

注意：打开一个话题时可能**立即就有一个在等的问题**（可能是几小时前问的）。
对话流要能正确渲染这种"历史里躺着一个未回答的提问"的情况，并把它显著标出来。

### 7.5 处理结论 → 关闭批注

1. 批注上出现 ★
2. 用户点开批注，看到 AI 写回的结论，以及一个跳转到对话出处的链接
3. 用户做决定：
   - 采纳 → 修改文档 → 把批注标为**已解决**（记录是哪次修改解决的）
   - 不采纳 → 标为**已驳回**
   - 还要再聊 → 拉进一个新话题（或原话题）继续
4. 标为已解决/已驳回后，文档上的锚点标记消失

一个话题聊 3 条批注，可能只解决 2 条 —— **结论是逐条写回、逐条处理的**，
没有"关闭整个话题"这种批量操作。

### 7.6 冷话题恢复

◌ 的话题点开时，后台需要重建会话并恢复上下文，会有可感知的延迟（数秒）。
需要一个明确的加载态，不要让它看起来像卡死。历史消息可以立即显示（它们是存好的），
只是"能继续对话"这件事要等。

### 7.7 裁决争用

**入口**：段落上的红色标记 / 改动条的争用数 / 提交界面里被拦住的项。

**界面**：并排（窄屏则上下）展示各版全文，每版标明来自哪个话题。

```
┌─────────────────────────────────────────────┐
│  段落 7 有 2 个版本                           │
├──────────────────────┬──────────────────────┤
│ 来自「术语对齐」       │ 来自「结构精简」       │
│                      │                      │
│ 完整段落文本…         │ 完整段落文本…         │
│                      │                      │
│ [ 采用这版 ]          │ [ 采用这版 ]          │
├──────────────────────┴──────────────────────┤
│ 原文：完整段落文本…（折叠）                    │
│                                             │
│           [ 都不满意，开个话题决定 ]           │
└─────────────────────────────────────────────┘
```

**只有两个出口**：

| 出口 | 行为 |
|---|---|
| 采用某一版 | 其余版本转为"未采纳"；对应话题被告知未采纳 |
| **开个话题决定** | 建新话题，各版提案 + 各来源话题自动作为引用带入 |

**明确不要做「手动编辑合并成第三版」。** 见 §1 的不变量：人不写正文。
想要一个都没提过的版本，就走第二个出口，在话题里说清楚，由 AI 写。

**不要做字符级 diff 高亮。** AI 改一段是整段重写，字符 diff 只会把整段标成红绿，
没有信息量，反而干扰阅读。展示完整的两版让人读，比标出每个字的差异有用。

超过 2 版时横向滚动或改为纵向列表，出口不变。

### 7.8 审阅并提交

**入口**：改动条上的「审阅并提交」。这是文档产生新版本的**唯一**途径。

```
┌───────────────────────────────────────────┐
│  审阅并提交                                │
├───────────────────────────────────────────┤
│  需求文档                                  │
│   ☑ 段落 3    来自「术语对齐」      [展开]  │
│   ⚠ 段落 7    2 个版本待裁决      [去裁决] │
│   ☑ 段落 9    来自「结构精简」      [展开]  │
│                                           │
│  接口文档                                  │
│   ☑ 段落 2    来自「术语对齐」      [展开]  │
├───────────────────────────────────────────┤
│  本次解决的批注：                           │
│   ☑ 批注 2   ☑ 批注 5   ☐ 批注 9          │
├───────────────────────────────────────────┤
│  变更说明：[                            ]  │
│                          [ 提交 3 处改动 ] │
└───────────────────────────────────────────┘
```

要点：

- **按文档分组。** 一次提交可能跨多篇文档，这是正常情况
- **默认全部勾选。** 想退回的才动手 —— 一个闸门，但很轻
- **争用项不可勾选**，只提供「去裁决」。裁决完回到这里，它变成可勾选项
- **争用不阻塞其他项**：8 处改动里 2 处争用，另外 6 处照常可以提交
- **「本次解决的批注」是提交的一部分，不是提交后的额外步骤。**
  这是批注从"待处理"变成"已解决"的唯一自然时机，别把它拆成两步
- 变更说明可留空，也可以让 AI 预填

**提交后**：每篇被改动的文档各产生一个新版本，勾选的批注转为已解决并记下是哪个版本解决的，
相关话题收尾转冷。文档上对应的标记全部消失。

**不要为"小改动"设自动提交的例外**（比如错别字直接应用）。一旦有例外，
用户就得开始猜"这次是自动的还是要我审的"，信任从这里开始崩。

## 8. 对话流的技术约束

设计对话区时需要知道的几条硬约束：

- **流式输出。** AI 的回复是逐片段推送的，需要打字机式渲染，并有明确的"本轮结束"标志。
- **一轮可能很长。** 分钟级是正常的。需要"进行中"的持续反馈，不能只有一个静态 loading。
- **引用失效会导致整条消息发不出去。** 如果用户引用的批注被别人删了，消息会被**整条拒绝**，
  而不是丢掉那条引用照发。需要一个明确的错误提示，指出是哪条引用出了问题，并允许移除后重发。
  （这是刻意的：半个问题比没问题更糟 —— AI 会对着它没看到的内容自信地作答。）
- **会话可能意外结束。** 后台进程可能退出，此时话题应转为 ◌ 冷态并提示，已有消息不丢。
- **离开页面不会中断话题。** 关掉浏览器标签，AI 还在跑。回来时状态应正确恢复。

## 9. 视觉优先级总排序

从最扎眼到最不起眼，设计时按这个顺序分配视觉权重：

1. ★ 批注有结论待你处理 —— AI 把活儿交回给人的时刻
2. ▍红 段落争用待裁决 —— 与上一项同级，都是"该你了"
3. ❓ 话题在等你回答 —— 不处理就永久卡死
4. 改动条（有争用时）/ 两个 tab 角标
5. ● 话题有未读
6. ▍蓝 段落有无争议的改动 —— 告知性
7. ◐ 批注讨论中 / ⏳ 话题进行中 —— 告知性，不需要行动
8. ○ 未决批注 / 闲置话题
9. ◌ 冷话题

前三项是整个界面存在的理由，其余都是背景信息。

三个"该你了"的状态必须**互相可区分**，它们要求的动作完全不同：

| | 在哪 | 要你做什么 |
|---|---|---|
| ★ | 批注锚点 | 看 AI 的结论，决定采纳或驳回 |
| ▍红 | 段落 | 在两个版本里选一个 |
| ❓ | 话题列表 | 回答 AI 的一个提问 |
