# 在 Rinto 里写文档

## 前提

**你写，人审。**

用户说「整理成文档」是让你产出成品，不是让你列个提纲请他填空。
不要把写作退回给用户。

反过来也成立：**审阅、选用、发布都不是你的动作**。
你对已有文档的修改是一条条「提案」，要等人看过、勾选、发布才会生效
（见「修改已有文档」）。不要试图去替人拍板，也不要绕过这一步。

## 何时建文档

建：

- 讨论收敛出了结论，且这个结论以后还要被人查阅
- 用户明确要求

不建：

- 过程性的推理、试探、比较 —— 那些留在对话里就好
- 只有一两句话的结论 —— 那属于批注，不是一篇文档
- 你拿不准要不要建 —— 问一句，别默认建

文档建出来就会出现在项目里被人看到。**建错的成本高于不建**，拿不准时倾向于问。

## 前提：你不需要配置任何东西

在话题里跑的时候，API 地址、token 和「你是哪个 AI」都已经由环境给好了
（`RINTO_API` / `RINTO_TOKEN` / `RINTO_CONVERSATION_ID`）。
`rinto-pmo config show` 能看到当前状态，其中 `conversation_id` 非空就说明你在一个话题里。

**不要运行 `config init`。** 那条命令是给人在自己机器上用的，
它会把这个 CLI 配成「代表某个人」—— 于是你写的东西会被署名成那个人。

**不要手工传 actor id。** 服务端从话题推导出作者,你传什么都不会被采纳。
内容的署名是这个系统最要紧的记录之一：「这段是模型写的还是人写的」必须一直答得出来。

## 怎么建

**标题和正文分开给。** 标题走 `--title`；**CLI 不会从正文里找标题**，
所以正文里的 `# 一级标题` 只是普通内容，不会被当成文档标题。

1. 把正文写成一个 markdown 文件，例如 `doc.md`
2. 先看一眼标题和分块对不对（不会创建任何东西）：

```
rinto-pmo doc create --title "标题" --body doc.md --dry-run
```

3. 没问题就去掉 `--dry-run` 真正创建

正文用 `#`、`##`、`###` 分节。**这三级的每个小节都会成为一个独立的 block**
（`####` 及更深的标题跟着它所属的小节走，不单独成块；
代码块、列表、引用里面的 `#` 是内容，不会被当成标题）。

切分由服务端做，`--dry-run` 问的也是服务端 —— 所以它和真正创建时的结果一定一致，
但它同样需要联通服务端，不能离线用。

顺带：正文开头一般不用再重复一遍文档标题 —— 标题已经在 `--title` 里了，
再写一遍只会让文档看起来把标题说了两次。但这是写法建议，不是限制。

block 是这个系统里批注、讨论、修改的最小单位，所以分节粒度应该接近
「一个可以被单独评论的片段」—— 一节讲一件事。
别把大段内容堆在一个 `##` 底下不分小节（那样任何人想评论某一点都只能评论一大坨），
也别碎到每句一节（那样批注会散得没法读）。

**不要自己拼 JSON。不要把正文当命令行参数传。**
长文本里的引号和换行在 shell 里会被吃掉，而且失败是静默的
—— 内容少了一半，命令还是成功退出。始终写文件、传 `--body`。

**需求文档。** 先用 `rinto-pmo requirement show <requirement-id>` 查看需求及其 documents 摘要，再用 `rinto-pmo doc show <document-id>` 读取已有文档。创建关联需求的文档时，传 `--requirement-id`，Project 会从需求推导，不需要再传 `--project-id`：

```sh
rinto-pmo doc create --requirement-id <requirement-id> --kind spec --title "登录规格" --body spec.md
```

文档类型为 `general`、`rfc`、`spec`、`plan`、`task`，任务清单类型用单数 `task`。需要筛选时用 `doc list --requirement-id <requirement-id> --kind spec`。同一类型可能有多篇文档，先检查已有内容，避免重复创建；已有文档的修改仍走提案审阅。

**独立文档落在哪个项目。** 没有指定 `--requirement-id` 时，省略 `--project-id` 会进默认项目，那是「不属于任何具体项目」的收容处，不是你正在谈的那个项目。

话题里引用了文档时，展开带着 `project_id`：

- 只引了一篇，或几篇都在同一项目：建的时候带上那个 `--project-id`，从属性里抄，不要手打
- 引了不同项目的文档：自己判断新文档属于哪边，拿不准就问，**不要省略参数把文档丢进默认项目**

`doc show` 也会在正文前打一行 `<!-- project_id: ... -->`，同一条信息，用法一样。

## 在正文里引用系统里的东西

写到「按上线流程的第二节做」「这条依赖那个任务」的时候，**写成链接，不要只写名字**。
名字会改、会重名；链接指向的是那个东西本身。

写法是**普通的 markdown 链接**，只是地址用 `rinto://`：

```markdown
需求见 [账号体系升级](rinto://requirement/01936f2a-1c4e-7c3a-9f1b-2d4e6a8b0c1d)，
先做 [接入 r-nacos](rinto://task/01936f2a-1c4e-7c3a-9f1b-2d4e6a8b0c1d)，
细节见 [上线流程的部署一节](rinto://block/01a023d8-8adf-7f41-b948-4cf1cb700f2d)。
```

### 地址从哪来：**搜，不要手打**

```sh
rinto-pmo search "部署流程" --type block --limit 5
```

每行**以完整地址开头**，直接复制粘进正文即可：

```
rinto://block/01a023d8-8adf-7f41-…  0.95  部署步骤  <- 上线流程
rinto://task/01a023e3-2a4a-7839-…   0.68  接入 r-nacos
```

**永远不要凭记忆或推断拼一个 UUID。** 36 位十六进制抄错一个字符，链接就指向不存在的
东西。已知类型的不存在目标会被服务端拒绝。地址从 `search` 输出复制，或使用
`list` / `show` / `create` 返回的真实 id。需求尚未进入语义搜索索引，使用
`rinto-pmo requirement list --project <slug> --parent-id all` 找到需求，
再用 `rinto-pmo requirement show <id>` 确认并读取内容；不要调用 `search --type requirement`。

### 资源地址，一个形状

```
rinto://requirement/{id}
rinto://project/{slug}        rinto://task/{id}
rinto://document/{id}         rinto://conversation/{id}
rinto://block/{id}            rinto://attachment/{id}
rinto://annotation/{id}       rinto://proposal/{id}
```

只有 project 用 slug，其余都是 UUID。**没有嵌套形式** —— block 就写
`rinto://block/{id}`，不要写成 `rinto://document/x/block/y`。
**不要用冒号**（`rinto://block:xxx` 会被解析成端口号，地址会静默损坏）。

### 指哪一层

- 指**需求本身**用 `requirement`；指它的规格、计划或任务清单文档仍用 `document`。
  正文中的引用不会设置文档归属；创建需求文档时仍需传 `--requirement-id`。

- 指**一整篇文档**用 `document`；指**文档里具体某一节**用 `block`。
  能指到 block 就指 block —— 读的人会被直接带到那一节，而不是从头找
- **话题（conversation）可以指，但那是指「那次讨论」**，不是把讨论内容搬过来。
  结论应该写在正文里，或者指向承载结论的批注

### 搜不到就先别指

`search` 的结果来自向量索引，**刚写完的内容需要几秒才会进去**。
如果你刚创建了一篇文档又想引用它，用创建时返回的 id，不要指望立刻搜得到。

搜不到、也没有 id 的东西，就用文字描述它，不要编一个地址。

## 出错了怎么办

命令失败，就把错误原样转达给用户，然后停下。

- **不要重试**。报错通常意味着有个真实约束在那里，重试只是撞第二次。
- **不要绕道**。尤其不要改用 curl 直接打 API 来「绕过」CLI 的报错 ——
  那个约束是服务端的，绕过去的结果是写进脏数据。

如果错误信息看不懂，把它原文给用户，别猜。

## 修改已有文档

**改动不会直接生效。** 你提出的是一条提案，挂在当前正文上等人审阅；
人看过、选定、提交之后才成为文档的新版本。

所以不要在提案之后说「已经改好了」—— 那不是实话。
说「已经提了修改,等你过一下」。

### 先看这篇文档上挂着什么意见

批注（annotation）是人和 AI 在文档上留下的**定点意见**：某一段哪里不对、为什么不该这么写。
它不在正文里，`doc show` 看不到它。

**改一篇已有文档之前，先看一眼还有哪些没了结的：**

```sh
rinto-pmo doc annotations <document-id> --unconfirmed
```

一行一条：批注 id、`open` 还是 `confirmed`、挂在哪个 block、开头一句。
挂在某个 block 上的批注，那个 block id 正是你要改的那一段。

`open` 意思是**没有人给它盖过章**，这个系统里批注只有这两种状态。
不要把它读成「等着谁去做」——一条批注可能只是记下一个疑问。

一条批注**光看第一句往往不够**：它下面可能已经有几轮追评，
而后面得出的结论跟最初那句抱怨常常不是一回事。

```sh
rinto-pmo doc annotation <document-id> <annotation-id>   # 读完整一条，含全部追评
```

**要落实的是整条线读下来的结论，不是最初那句抱怨。**
追评里有人写的也有 AI 写的（人可以点一个按钮让 AI 答一条），
命令不区分作者 —— 谁说的不改变那句话讲得对不对。

三条纪律：

- **不要自己去确认（confirm）批注。** 给批注盖章是人的动作，跟提交提案一样。
  你能做的是提一条把它解决掉的改动，然后说「这条提案对应那条批注」。
- **不要把批注当需求清单一次性全做掉。** 有的批注在等人先拿主意；
  拿不准的就把它念给用户听，问他要不要现在改。
- **看不懂一条批注在说什么就问**，不要顺着字面猜一个改法提上去。

### 再看一眼：谁引用了这篇

一份文档里的决定会被别处**照着写进正文** —— 别的文档、任务描述、批注。
你把这里的决定改掉，那些地方还在说旧的那一套，而它们不会自己跟着变。

```sh
rinto-pmo doc backlinks <document-id>
```

按来源类型分组，每条两行：文本在哪（类型 + id，是文档里的一段就带上所属文档），
以及**它把这篇文档叫作什么**（`as "..."`）。

那个 label 是最值钱的一行。一条写着 `as "三态生命周期"` 的引用，
在三态被砍掉之后就已经在说假话了 —— 尽管它带的地址还解析得开，
所以光看链接活不活是看不出来的。

`nothing points at this document` 是个真答案：没人引用，改这篇不牵动别处。

**发现了牵连怎么办：**

- **同一个话题可以对多篇文档分别提案。** 一次讨论改 N 篇是正常的，
  `doc propose` 对每篇各发一次即可，它们会挂在同一个话题下等人一起审
- **不要顺手把别人那篇也改了。** 先把牵连讲给用户听：
  「改这个会牵动 X 和 Y，要不要一起提？」由他决定范围
- 引用里有的是**顺带提一句**，不是照抄决定。看 excerpt 判断，判断不了就问

### 三种输入方式，按改动的形状选

**一次 `doc propose` 只能选一种输入方式。** `--title` 和 `--body` 互斥，
不能放在同一条命令里；`--block` 必须和 `--body` 一起用。
`doc create` 则需要同时传 `--title` 和 `--body`，不要把创建时的参数组合照搬到提案命令。

**每次提案都要先读一遍文档，并把读到的 revision id 带上。**
`doc show` 和 `doc show --working` 的输出里都有一行
`<!-- base_revision_id: ... -->`，把那个值原样传给 `--base-revision-id`。

这不是格式要求。服务端拿这个值判断你的改动是**从哪份正文改起的**：
带错了，一份基于昨天正文的重写就会被当成对今天正文的意见，把中间别人提交的东西
静默地改回去。**不要临发请求时另外查一个"最新" id 顶上。**

**整篇输入** —— 最常用，也是唯一能表达结构性改动的方式：

```sh
rinto-pmo doc show <document-id> --working        # 读，记下 base_revision_id
rinto-pmo doc propose <document-id> --body new.md \
  --base-revision-id <上面那一行的值> --change-summary "拆出监控一节"
```

传整篇 markdown。**拆一节、合两节、加一节、删一节、调顺序，只有这种输入能表达。**

服务端会自己算出差异，然后把它**拆成一条条独立的提案**：改一段是一条，加一段是一条，
删一段是一条，挪一段是一条。响应里列出来的就是它们。

**没有"整篇提案"这个东西。** 一次重写如果改紧了两段、加了一节、删了一句过时的注，
那就是四件事，人会对这四件事有四种意见 —— 他可能只要其中两件。所以没有一个 id
代表"这次重写"，你也不能把它当成一个整体去讨论或让人一次性接受。要讨论就引用具体
那几条。

内容没变的小节保持原样不动，挂在上面的批注因此不会掉。搬了位置但文字没变、而且不会
认错的段落会被认成"移动"，id 也一起保留。

`--change-summary` 是给审阅的人看的一句话，会跟着本轮拆出的每条提案走。

**只改一段** —— 改动明确落在某一节，而且不涉及结构：

```sh
rinto-pmo doc show <document-id> --with-block-ids   # 先看每段的 id 和 base_revision_id
rinto-pmo doc propose <document-id> --block <block-id> --body one-section.md \
  --base-revision-id <读到的值>
```

`--body` 这里只放那一段的新内容，不是整篇。

**改标题**：

```sh
rinto-pmo doc propose <document-id> --title "上线与回滚流程" \
  --base-revision-id <读到的值>
```

标题是独立的字段，**永远不从正文里读** —— 所以正文里的 `# 一级标题` 改不动文档标题，
要改标题就用这条命令。**标题和正文都要改时，分两次调用 `doc propose`：一次传
`--title`，另一次传 `--body`（只改一段时再带 `--block`），每次都带上对应的
`--base-revision-id`。** 只改正文时不需要传标题。
标题提案和正文提案可以并存、互不影响；标题提案和别人的标题提案之间就是一次普通的二选一。

### 拿不准用哪种：仍然传整篇

整篇输入表达力最强，而且不需要任何 block id。它只是输入格式，服务端仍会把它拆成
一条条局部改动。只有在「改动确实只落在一节、且你已经知道是哪一节」时，`--block`
才更省事。

### 提案 id 是固定的，改主意就是新的一条

一条提案 id 永远指同一份修改：内容、目标、位置和它是从哪份正文改起的，写下来就不再变。
聊天里引用了它，那条引用以后打开还是当时那份东西。

所以**改主意不是原地改，而是新提一条**：原来那条变成 superseded，新的一条是新 id。
一模一样地再提一次则会复用原来那条（id 不变），不会平白多出一条。

再提一次整篇，只替换**你这个话题**在这篇文档正文上挂着的东西；你的标题提案和别人的
提案都不动。响应里的 `superseded` 会列出本轮撤下的旧提案 —— 看到非空列表时，
确认一下有没有漏掉上一轮仍想保留的改动。

### 提之前，先读回你自己的工作版

这一条没有报错保护你，所以要自己当心。

`rinto-pmo doc show` 给的是**已发布的正文**。你挂着的提案还没被人发布，
所以**不在里面**。基于它再提一次，等于拿一份不含你自己改动的文本去算差异 ——
你上一轮的改动会被当成"没提过"，命令还成功，没有任何警告。

要看自己的工作版，加 `--working`：

```sh
rinto-pmo doc show <document-id> --working
```

它把你这个话题挂着的、当前还能应用的改动叠加到正文上，标出哪几段是你的提案（`*`）、
哪几段别人也在改（`!`），并且用 `!` 单独列出你挂着但**已经没法应用**的那几条
（比如它要改的段落被人删了）。那是给你看的信息，不是错误：那几条得重新提。

**它是算出来的视图，不是分支，也不是草稿** —— 不存在任何地方，下次问就重新算一遍。

整篇重写还有另一半风险：它是按「你给的正文 vs 你读到的那份正文」算差异的。
如果你手上是很旧的文本却当成新的传上去，差异里就会出现「把那几段改回去」。
`--working` 同样解决这一半 —— 它顶替的是**当前**正文，`base_revision_id` 也是它给的。

什么时候尤其要读：

- 同一次会话里隔了很久，中间你自己提过案
- 你打算基于「记忆里的版本」或自己拼接的旧内容去改
- 不确定中间发生过什么

（会话被重开时不用担心：系统会把当前正文和你还挂着的提案一并交回给你。
`--working` 是给**同一次会话里**的情况用的 —— 注入只发生在重开的那一刻，
你之后自己提的案不会再注入一次。）

### 看看自己挂着哪些改动

```sh
rinto-pmo doc proposals <document-id> --mine --status live
```

一行一条，说明它是哪种改动（改/加/删/移）、落在哪个 block，以及改动摘要。
标题提案只在这里看得到，`--working` 不显示标题。

### 别人也在改同一处

提案返回里会点名说「你这条和某某条抢同一件事」，`doc show --working` 也会用 `!`
标出来。这是**告知，不是错误** —— 两个版本并存，由人来选。

想看清楚都有哪些分歧：

```sh
rinto-pmo doc contentions <document-id>
```

它列出的是**两两一对**：这一条和那一条不能同时成立，以及为什么。
不是分组 —— 同一段的"改写"和"移动"可以同时要，虽然它们各自都和"删掉这一段"冲突。

`--working` 只代入你这个话题自己的提案，别人要改成什么样不在那里。读一条：

```sh
rinto-pmo doc proposal <document-id> <proposal-id>
```

看到争用的时候，把情况说给用户听，然后停下等他决定。
不要为了「赢」而反复改自己那条。用户明确要你融一版时除外。

### 正文在你提案之后变了

不用做任何事，也没有 rebase 这回事。你的提案原封不动待着，服务端每次读的时候
重新和当前正文比一遍：

- 别处改了 —— 你的改动照样能用
- 你要改的那一段被人改了 —— 会标成"要重新确认"，由人重新选一次
- 你要改的那一段被删了 —— 会标成不可应用，那条得重提
- 你想要的结果别人已经写成了 —— 会标成已经生效，不会再发一次

你要做的只是在再次修改之前 `--working` 读一遍，然后带上那次读到的
`base_revision_id`。

## 回复批注

批注是有人指着某一段说这里不对。用户让你回应时，答在**那条线程底下**，
不要答在聊天里 —— 结论落在批注，过程才落在对话。

```sh
rinto-pmo doc annotation-reply --help
```

写在文件里传 `--body`，理由跟正文一样：回复是散文，散文里有换行和引号。

**一次一条。** 三十条批注就调三十次，每次都会告诉你这一条成没成 ——
这才有可能回报「三十条回了二十八条，另外两条是因为什么」。

**你只是在说话，不是在改文档。** 回复改不了正文，也关不掉那条批注 ——
确认是人的动作。所以论证你的看法，不要描述一个你接下来要做的修改，
那个修改不会从这里发生。想改就去提案（见上）。

## 留批注

批注是**结论**：指着某一段说这里不对，然后等人决定。跟回复一样，它落在文档上，
不落在聊天里。

```sh
rinto-pmo doc annotate --help
```

`--block` 要的是**真的 block id**，不是提示词里那个 `[block:b1]` 标签。
先取一遍：

```sh
rinto-pmo doc show <document-id> --with-block-ids
```

**不要编 block id。** 编出来的 id 不会报错，只会让这条批注变成「不知道在说哪一段」——
命令打印的那行会告诉你 unanchored，看一眼。

**说问题，不要说你打算怎么改。** 批注改不了文档，也不会被应用；
要改就去提案（见上）。

## 不要做的事

- **不要新建一篇「修订版」文档来代替修改。** 会留下两篇内容冲突的文档
- **不要把改动写成批注充数。** 批注是结论,不是改动
- **不要绕过 CLI 直接打 API。** 提案的署名、作用域、争用检测都在服务端,
  绕过去写进的是脏数据
- **不要替人发布或选用,也不要替人确认批注。** 那是人的动作,也是这套流程存在的原因
- **不要凭空编一个 `--base-revision-id`。** 它必须来自你这次真读到的那一行；
  随手填一个"最新的"会把别人的改动静默改回去
- **不要手打 `rinto://` 地址里的 UUID。** 抄错不会报错,只会变成一条指向虚无的链接
