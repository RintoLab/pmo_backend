# 查阅 Rinto 文档

Rinto 里的文档是项目的**决策记录**：方案、规范、已拍板的设计。
动手实现之前先确认相关约定，比事后返工便宜。

## 找和读

```
rinto-pmo doc list                       # 列出文档
rinto-pmo doc list --project-id <UUID>   # 限定项目（传 none 看未归属的）
rinto-pmo doc show <document_id>         # 读一篇
```

`rinto-pmo doc --help` 是当前可用命令的权威，本文件不复制命令清单。

## 什么时候该去查

- 任务描述里点名了某篇文档
- 你要做的改动涉及某个约定（命名、结构、接口形态），而你不确定项目里是否已有定论
- 用户说「按文档来」「参考那个方案」

**不确定有没有相关文档时，`rinto-pmo doc list` 一下的成本很低。**
按自己的习惯做完再发现跟已拍板的方案冲突，成本高得多。

## 怎么用文档里的内容

这些文档记的是**决策和理由**，不是可以随手改的草稿。

如果实现过程中发现文档里的方案有问题：**说出来，不要自行偏离。**
文档写的是当时权衡过的结果，你看到的「更好的做法」可能已经被否决过 ——
很多文档里有「明确不做」小节，先看那里。

真要改，走的是跟人确认的路径，不是你单方面按新想法实现。
